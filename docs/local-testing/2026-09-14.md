# Local machine test log: 2026-09-14

This log records visible, manually operated fmri-gym sessions on one workstation
on September 14, 2026 (UTC+08:00). It covers 22 selected games/scenarios and explains
the evidence behind the [machine recommendations](../../MACHINE_REQUIREMENTS.md).
It does not establish the minimum CPU, RAM, or GPU that can run them.

## Measurement method

- The participant played each game manually in a visible fmri-gym window. No
  automated game-control keys were sent. Later sessions waited for manual readiness
  and trigger input after an unattended trial was identified and excluded.
- An external monitor sampled the observed game process tree approximately every
  0.5 seconds. CPU values use **100% for one logical processor**, not the whole
  32-thread machine. Recorded RSS is a sum of observed processes and can double-count
  shared pages. It is not total system memory or a minimum RAM requirement.
- WSL process RSS excludes the rest of the Linux VM, WSLg, and Windows host. Whole
  NVIDIA-card samples included unrelated applications and were not used as game
  VRAM requirements. Short peaks between samples may be missed.
- Step frequencies and intervals come from `.npz` `session_time` values. They
  describe logged updates, not measured monitor refresh or input-to-photon latency.
  Turn-based waits are not FPS measurements; every logged action is counted,
  including action code zero, which can be a valid direction.
- Foreground-window screenshots were sampled roughly every 10 seconds. Captures
  were checked against run timestamps and image contents; screenshots containing
  the editor instead of the game were rejected. Deadly Corridor has no retained
  gameplay screenshot. Captures do not provide continuous video evidence.
- Later runs report resources from game onset + 5 seconds through offset - 0.5
  seconds. Earlier Windows samples use different coverage, identified below.
  Browser interval summaries exclude initial startup and episode boundaries.
  SuperTuxKart additionally excludes the first five seconds of each episode from
  steady intervals and reports reset gaps separately.

## Findings and unresolved limits

### Browser update rate and KIA

The AI GameStore curricula already specify **10 FPS**. This was a project setting,
not a limit introduced by the resource monitor. Achieving 10 logged updates/s does
not establish that an action game feels smooth or that it can sustain 30 or 60 FPS.
The participant reported visibly slow motion, particularly in game3.

Before the patch, manual game3 trials recorded approximately 1.04-1.07 updates/s.
The browser was serializing a large Three.js state graph on every step. A separate
15-second diagnostic on the same Windows machine compared the original transfer
with filtering to scalar fields inside the browser:

| Diagnostic metric | Original transfer | Scalar transfer |
|---|---:|---:|
| Mean state-read time | 784.84 ms | 2.24 ms |
| Mean total step time | 800.11 ms | 12.89 ms |
| Mean screenshot/render time | 59.50 ms | 37.09 ms |
| Logged updates/s after initial 5 s | 1.11 | 9.99 |

The scenes and manual actions differed, so the render-time difference cannot all be
attributed to the patch. The state-read timing identifies a software bottleneck on
this machine. The selected patched manual game3 run then reached 10.00 updates/s
with 817 input-bearing steps and visible gameplay. Its p95 step interval was
110.46 ms; process-tree CPU averaged 64.8% of one logical processor, with p95 91.2%.
These observations do not justify a hardware upgrade or isolate an OS effect.

The local patch preserves top-level scalar state used by the adapter, including
async state retrieval, while dropping nested scene objects and DOM placeholders.
It does not make all logged state fields identical to the original implementation.
It also does not establish seeded browser replay or improve the screenshot path.

Restart controls remained a separate issue. In game4, `R` returns to the start
screen and `RETURN` starts play. The selected retry contains 285 PLAYING steps, 38
loss-screen steps, and 257 START steps. The adapter's existing terminal-state handling
does not recognize every browser game's win/loss label, so a manual restart may
remain inside one logged episode. Very short key presses can also be missed by the
10 Hz held-key polling. These limitations remain outside this documentation change.

### MiniHack controls and apparently static screens

Room 5x5 uses a fixed room layout and a player-centered crop. Repeated successful
episodes can therefore look like the same screen. Logged coordinates and 28
positive-reward terminations in the selected run show that the environment advanced.

Corridor's open/kick actions require two inputs: press and release `O` or `K`, then
press a direction toward the door. The graphical crop omits the full TTY prompt;
logs showed `In what direction?` and invalid repeated-letter responses. After using
the two-step command, the final retry showed an open passage and one successful
termination. Eat similarly used `E` followed by `Y`; the short run recorded nine of
each and nine positive-reward terminations. These were not CPU-load failures.

### SuperTuxKart and WSL graphics

The selected race used SD graphics, a 600 x 400 internal image, three karts, and the
configured 30 updates/s. Race screenshots, 2,034 input-bearing steps, and 3,019
within-episode distance changes confirm activity. Three episodes were recorded;
two ended by truncation and none by termination. Race completion was not verified,
and final subjective confirmation of picture/control quality was not recorded.

The steady logged update rate was 30.00 updates/s, with p95 intervals of 33.88 ms
and a maximum interval of 36.70 ms.
Episode reset gaps were **586 ms and 1,164 ms** and are excluded from those steady
figures. Process-tree CPU averaged 18.2% of one logical processor (p95 24.0%);
sampled peak RSS was 540.6 MiB. These values exclude WSL infrastructure overhead.

Independent graphics-context checks after the games reported Chrome using ANGLE
with the RTX 4080 through Direct3D 11, and WSL OpenGL using D3D12 with AMD Radeon
graphics (OpenGL 4.2, Mesa 23.2.1). These checks identify available renderer paths;
they are not per-game GPU measurements or evidence that an old integrated GPU will
perform equivalently.

| Corridor first retry | 213 actions in approximately 84 s, but door-command confusion and no success; superseded by keyboard retry |

The Corridor display failure logged `rdp_allocate_shared_memory`, an I/O error,
and disabled graphics redirection. Its symptoms matched the upstream
[WSLg/OpenVMM report](https://github.com/microsoft/openvmm/issues/4274).
A complete WSL restart recovered the display. The initial SuperTuxKart launch also
produced two windows, complicating focus. These observations do not measure game
compute requirements.

## Evidence retained

The accompanying [results JSON](2026-09-14/results.json) is a curated extraction from
per-run manifests, `.npz` action/reward/time arrays, resource samples, and measurement
summaries. Its run identifiers map to the locally retained `visible-local-tests`
archive. Raw archives, environment profiles, and desktop screenshots remain local;
this repository contains the summary, not the complete raw benchmark dataset.

The [archived patch](2026-09-14/browser-state.patch) records the browser code variant.
It is provided for provenance, not as a claim that the fix has been merged. Sampling
was external to the project; no production benchmarking code was added.

These short, single-machine observations support testing the proposed minimum and
recommended configurations on the actual experiment computer. They do not determine
a calibrated hardware tier for each game, certify 4 GB operation, or cover a full
experiment's thermal behavior, long-term memory growth, or physical stimulus timing.
