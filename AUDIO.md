# Game audio

ViZDoom and stable-retro play their native PCM through the session's shared
`Audio` output by default. Other adapters currently return no sound. Browser
games do not forward their audio into this output.

## Why some games are silent

Playback requires both sound generated by the environment and an adapter that
exposes its PCM through `sound()`. A game's original desktop release having sound
does not guarantee that its Gym environment provides audio samples.

| Backend | Current playback support and reason |
|---|---|
| ViZDoom | Supported: the engine provides stereo PCM through its audio buffer. |
| stable-retro | Supported: the emulator provides native PCM and its sample rate. |
| AI GameStore | Not integrated: browser screenshots transfer image pixels, not browser audio. |
| MiniHack / NetHack, Crafter, Baba, Rush Hour | Their current adapters expose visual or symbolic state, with no PCM output hook. |
| ALE, generic Gym, VGDL, Overcooked | Their current adapters do not forward PCM to the shared output; availability depends on the environment. |

Setting `"audio": true` cannot add sound to an environment or adapter that does
not provide it. fmri-gym does not invent sound effects for silent environments;
the game presented to a participant should remain the environment being evaluated.

## Controls and timing

Mute every game with `--no-audio`, or set `"audio": false` on one game phase.
These controls mute playback; they do not change actions, rewards, or
ViZDoom's audio observations and recordings. For ViZDoom only,
`"env_kwargs": {"audio_buffer_enabled": false}` disables PCM production and
removes its audio observations/log fields. An explicit engine setting takes
precedence over the adapter's default.

```bash
python fmri_play.py --subject sub-test --dummy-trigger --curriculum configs/demo_retro_audio.json
python fmri_play.py --subject sub-test --dummy-trigger --curriculum configs/demo_retro_audio.json --no-audio
```

Run game steps at the engine's native rate for continuous playback. ViZDoom
needs `fps * env_kwargs.frame_skip == 35` (`frame_skip` defaults to 1).
Airstriker's Genesis core runs at approximately 59.9227434 frames/s, as used in
the demo. Other retro cores may differ. No resampling or game-speed adjustment
is performed by the audio output; slower production leaves silence, and
sustained faster production eventually drops pending chunks.

An adapter exposes `sound() -> Sound | None`, where `Sound` contains native
`pcm` samples shaped `(samples, channels)` and their `sample_rate`. The sample
rate may be fractional. `Session` passes the result to `Audio.play()`; the
output opens lazily and reopens only if rate, channel count, or dtype changes.
Different chunk lengths do not reopen the device. Engines with no PCM
integration keep returning `None`.

The output queue copies each retained chunk because engines can reuse their
buffers. Its callback consumes partial chunks exactly once and fills missing
samples with silence without waiting for the game thread. At most 32 chunks
are pending, plus the current chunk; overflow discards the oldest pending
chunk to bound backlog. Each playback start retains the existing 100 ms silence
prefill and requested 100 ms PortAudio latency. Pending audio is discarded at
each episode boundary, including ESC and exceptions, and the device is closed
when the session's CLI exits.

ViZDoom logs the environment's generated PCM in each block's `audio` array,
with `audio_sampling_rate` alongside it. Terminal rows remain aligned with
`actions` and `rewards`. This is generated audio, not a measurement of what the
speakers actually emitted: mute, underruns, overflow, and output latency can
make playback differ. Retro audio is played from the native emulator buffer;
it is not stored as a separate PCM array in the current log format.

Playback uses the default output device. Linux retains the system ALSA mixer
selection used by the existing output. ViZDoom retains the `+snd_efx 0`
workaround for its OpenAL reverb crash. A device-open failure is reported to
the caller rather than silently claiming playback succeeded.

Scanner audiovisual synchronization still requires measurement on the actual
presentation hardware. Frame timestamps and generated PCM do not establish
the physical display/speaker onset delay.
